# Prometheus Constitution

## Purpose

The Prometheus Constitution is the permanent engineering foundation for Prometheus. It defines the rules that govern every future engineering session, every AI-assisted development session, every repository change, and every product decision made inside the Prometheus codebase.

This document exists to protect continuity, prevent duplicate work, preserve founder knowledge, enforce security, and keep Prometheus moving forward through verified progress rather than assumptions.

## Existing Work Verification Law

Before writing or modifying code, creating documents, changing configuration, deploying, committing, or introducing a new system, the current state of Prometheus must be verified.

Every engineering session must first search and verify:

- GitHub repository
- Current branch
- Prometheus IQ dashboard
- Prometheus OS
- Prometheus Companion
- Local project folders
- Home and project files
- Reports
- Documentation

The session must answer:

1. Is this already built?
2. Is it partially built?
3. Where does it already exist?
4. Should it be reused?
5. Should it be improved?
6. What should not be duplicated?

If the work already exists, improve it. Do not rebuild it. Do not create duplicate systems, duplicate dashboards, duplicate documents, duplicate agents, duplicate workflows, or duplicate architecture unless Cruz explicitly approves that decision.

## The Seven Prometheus Doctrines

### 1. Prometheus Engineering Doctrine

Prometheus engineering work must be deliberate, verified, and production-minded. Do not take shortcuts. Do not use temporary workarounds. Do not simulate success. Do not fake implementation. Do not mark work complete unless the real system behavior proves it works.

### 2. Disaster Recovery & Business Continuity Doctrine

Prometheus must remain recoverable. Important work must be preserved through clear file organization, safe GitHub backups, documented setup paths, and recovery instructions that a future founder, employee, contractor, or AI system can follow.

### 3. Founder Continuity Doctrine

Prometheus must not depend only on Cruz's memory. Founder decisions, company context, operational processes, product direction, and important milestones must be captured so the company can continue operating even when context shifts, time passes, or new collaborators join.

### 4. Knowledge Preservation Doctrine

Prometheus knowledge must be organized, durable, and searchable. Product history, technical history, business history, pilot history, customer context, and operating procedures must be preserved in the correct place instead of being scattered across temporary notes or one-time conversations.

### 5. Prometheus Security Doctrine

Prometheus must protect secrets, customer data, business data, location data, source code, credentials, tokens, API keys, and private operational intelligence. Do not expose secrets. Do not commit secrets. Do not print secrets. Do not weaken security controls without explicit approval and documented justification.

### 6. Prometheus Truth Doctrine

Prometheus must distinguish verified facts from assumptions, estimates, and unknowns. Do not invent evidence. Do not overstate progress. Do not claim something is complete, deployed, tested, connected, secure, or live unless it has been verified.

### 7. Prometheus Certification Review Doctrine

Before major work is treated as complete, it must pass a final review against the actual user experience, repository state, security requirements, and stated acceptance criteria. Scripts, isolated tests, or partial checks are not enough when the real product experience is the acceptance standard.

## Governing Statement

This Constitution governs every future Prometheus engineering session unless Cruz explicitly changes it. All future Prometheus work must begin by respecting this document, verifying existing work, preserving continuity, protecting security, and advancing the company through truthful, non-duplicative, verified progress.
