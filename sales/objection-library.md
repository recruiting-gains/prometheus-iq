# Objection Library

Purpose: provide consistent, truthful responses to common sales objections.

## Positioning Objections

### "Is this just a CRM?"

Response:

No. CRM starts once there is a lead, contact, account, opportunity, or task to manage. Prometheus focuses on the field work before and during that moment: where reps should go, what happened at each visit, which locations produce, and how the next route improves.

Follow-up:

- What does your CRM fail to show about field activity before a lead exists?

### "We already use Salesforce, HubSpot, or another CRM."

Response:

That is expected. Prometheus is designed to sit beside the CRM, not replace it. The value is field execution intelligence: route focus, visit outcomes, and learning from activity that often never reaches the CRM.

Follow-up:

- Where do reps decide where to go today?
- How much of that decision-making is visible in the CRM?

### "We already use a route planner."

Response:

Route planners optimize directions. Prometheus is about sales productivity. It helps teams decide which locations are worth visiting, capture outcomes, and learn which routes actually produce.

Follow-up:

- Does your route planner tell you which stops create qualified outcomes over time?

## Pilot Objections

### "We do not want a big rollout."

Response:

The recommended next step is not a rollout. It is a controlled pilot with approved users, clear data rules, success metrics, and a decision point.

Follow-up:

- What pilot size would be operationally safe for your team?

### "We need IT/security/legal/HR review."

Response:

That is appropriate. Prometheus should be evaluated with clear access, data, privacy, and user-consent boundaries before broader deployment.

Follow-up:

- Who needs to review the pilot scope before approval?

### "We do not want reps to feel tracked."

Response:

Prometheus should be positioned as field execution support, not surveillance. The pilot should define exactly what is logged, when verification is used, who can review it, and what is not being tracked.

Follow-up:

- What language would make the pilot feel fair and clear to reps?

### "A pilot will distract the team."

Response:

The pilot should be narrow enough to avoid disruption. Training should be short, logging should happen inside the field workflow, and review should focus on whether the tool improves execution without adding heavy admin work.

Follow-up:

- Which team or territory could test this with the least disruption?

## Value Objections

### "How do we know this will increase sales?"

Response:

We should not claim that before measurement. The pilot should test whether Prometheus improves the controllable inputs that lead to sales: better route focus, more useful visits, better follow-up capture, and clearer manager visibility.

Follow-up:

- Which leading indicators matter most before a closed sale happens?

### "What is the ROI?"

Response:

ROI depends on the value of each qualified outcome, rep cost, field activity volume, and expected improvement. The pilot should collect the minimum data needed to calculate whether better field execution pays for the system.

Follow-up:

- What is a qualified appointment, inspection, unit, or lead worth to your business?

### "Our reps already know where to go."

Response:

Experienced reps have valuable judgment. Prometheus does not replace that judgment; it turns it into a measurable learning system so the whole team can see what works and improve faster.

Follow-up:

- How do new reps learn the best locations or territories today?

## Product Scope Objections

### "Can it integrate with our CRM?"

Response:

Integration may be valuable later, but the first question is whether Prometheus improves field execution. A pilot should avoid unnecessary integration complexity unless integration is required to prove value.

Follow-up:

- What minimum data would need to move between systems for a pilot?

### "Can you customize it for our industry?"

Response:

Prometheus is built around a reusable field-sales workflow, with industry-specific language, metrics, and qualified location logic layered on top. Customization should start with terminology and success metrics, then expand only where proven necessary.

Follow-up:

- What words does your team use for field activity and successful outcomes?

### "Can this replace manager ride-alongs or manual reporting?"

Response:

Prometheus can reduce blind spots and improve reporting, but it should not be sold as a full replacement for management. It gives managers better evidence for coaching and operating decisions.

Follow-up:

- Which manual reports or check-ins consume the most manager time today?

## Commercial Objections

### "This is too early."

Response:

That may be true for a broad rollout. A controlled pilot is how both sides decide whether the value is real before making a larger commitment.

Follow-up:

- What would need to be true for this to become worth evaluating?

### "We do not have budget."

Response:

Then the pilot should only proceed if there is a realistic path to budget after evidence. A pilot without a commercial path creates work without a decision.

Follow-up:

- If the pilot proves value, where would budget come from?

### "Send me information."

Response:

I can send a concise overview, but the useful next step is a short discovery conversation. The value depends on your field motion, metrics, and current tool gaps.

Follow-up:

- Would a 20-minute discovery call be more useful than a generic packet?

## Competitive Objections

### "Why not use spreadsheets?"

Response:

Spreadsheets can collect data, but they do not create a field operating rhythm by themselves. Prometheus is designed around daily rep decisions, visit logging, manager visibility, and learning loops.

### "Why not use Google Maps?"

Response:

Maps help with navigation. Prometheus helps decide which locations are worth visiting and whether those visits produce outcomes.

### "Why not build this internally?"

Response:

An internal build may be possible, but it requires product design, field workflow, route intelligence, reporting, onboarding, support, and ongoing iteration. The pilot should determine whether the problem is worth solving before investing in internal build cost.

## Objection Handling Rule

Do not argue the buyer into agreement. Use objections to identify missing proof, risk concerns, or misalignment. If the objection reveals no field-sales problem, disqualify the opportunity.
