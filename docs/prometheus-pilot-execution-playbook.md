# Prometheus Pilot Execution Playbook

Scenario: Dallas approves a 14-day Prometheus IQ pilot  
Pilot size: 3 approved users  
Scope: LSM field sales activity  
Active capabilities: GPS verification, Route Intelligence, visit logging, field outcome tracking  
Purpose: Give the founder a step-by-step operational guide if pilot approval happens.

## 1. Day 0 Setup

Day 0 is the preparation day before users begin logging field activity.

Founder checklist:

- Confirm pilot approval in writing.
- Confirm the 3 approved users.
- Confirm approved manager / reviewer.
- Confirm pilot start date and end date.
- Confirm weekly review date.
- Confirm final report recipient list.
- Confirm HR/legal requirements before users begin.
- Confirm user consent is signed or approved.
- Confirm no sensitive company data should be entered unless approved.
- Confirm Prometheus IQ access works for each user.
- Confirm each user knows how to open the app on their phone.
- Confirm each user understands GPS verification is visit-based, not continuous tracking.
- Confirm each user understands what to log after each field visit.

Day 0 success means every user can access the app, understands the pilot rules, and knows what success looks like.

## 2. User Onboarding Process

Keep onboarding short. The goal is adoption, not a long training session.

Recommended user onboarding:

1. Explain the pilot purpose.
   - "We are testing whether Prometheus IQ helps field activity become more focused, verified, and measurable."

2. Explain what users need to do.
   - Check the suggested route or next location.
   - Go to approved field locations.
   - Log the visit after the interaction.
   - Use GPS verification only when intentionally logging a visit.
   - Record conversations, leads, units, follow-ups, and notes.

3. Explain what users should not do.
   - Do not enter sensitive company data unless approved.
   - Do not enter private customer information unless approved.
   - Do not fake visits or locations.
   - Do not treat the app as continuous tracking.

4. Run one practice log.
   - Have each user complete a sample visit log before the pilot starts.

5. Confirm user confidence.
   - Ask: "Can you use this in the field without slowing down?"

## 3. Manager Onboarding Process

Manager onboarding should focus on visibility, expectations, and review cadence.

Recommended manager onboarding:

1. Review the pilot purpose.
   - Improve LSM visibility, accountability, route usefulness, and measurable outcomes.

2. Review what managers should look for.
   - Are reps logging visits?
   - Are GPS verified visits being used appropriately?
   - Are leads, units, and follow-ups being captured?
   - Are patterns emerging by location, category, or time window?

3. Review what managers should not do.
   - Do not treat Prometheus IQ as a surveillance tool.
   - Do not judge the pilot only by one bad day.
   - Do not change the pilot scope without approval.

4. Confirm weekly review process.
   - Review activity, adoption, outcomes, user friction, and next steps.

## 4. Daily Founder Responsibilities

Every pilot day, the founder should act like an operator.

Daily founder checklist:

- Confirm the app is accessible.
- Confirm users understand the day’s expectations.
- Check whether users are logging field activity.
- Watch for missing logs or confusion.
- Collect user feedback quickly.
- Record any app issues or adoption issues.
- Track daily metrics.
- Do not add new features during the pilot unless required to fix a serious issue.
- Keep notes for the final report.
- Prepare a short daily summary.

Founder daily summary format:

- Approved users active:
- Visits logged:
- GPS verified visits:
- Leads generated:
- Units sold:
- Follow-ups created/completed:
- Field time logged:
- User friction:
- Manager concern:
- Action needed tomorrow:

## 5. Daily Rep Responsibilities

Reps should keep the workflow simple.

Daily rep checklist:

- Open Prometheus IQ before beginning field activity.
- Review the suggested field direction.
- Visit approved locations.
- Log each meaningful visit.
- Use GPS verification when intentionally logging a visit.
- Record:
  - Location.
  - Time window.
  - Conversations.
  - Leads.
  - Units.
  - Follow-ups.
  - Notes.
- Complete follow-ups when needed.
- Tell the founder or manager if anything is confusing or too slow.

Rep success means the user can complete field work and log results without feeling buried in admin work.

## 6. Weekly Review Process

The weekly review should be short and focused.

Recommended length: 20 to 30 minutes.

Review agenda:

1. Activity review.
   - Locations visited.
   - GPS verified visits.
   - LSM events attended.
   - Time spent in field.

2. Outcome review.
   - Leads generated.
   - Membership units sold.
   - Follow-ups created.
   - Follow-ups completed.
   - Conversion rate.
   - Productivity per field session.

3. Adoption review.
   - Are users logging consistently?
   - Is the workflow fast enough?
   - Are users confused by anything?

4. Manager visibility review.
   - Is leadership seeing field activity more clearly?
   - Are any location/category/time-window patterns emerging?

5. Decision.
   - Continue as planned.
   - Continue with minor process adjustment.
   - Pause for concern.
   - Stop pilot if needed.

## 7. Common Pilot Failure Points

Common failure points:

- Users forget to log visits.
- Users log at the end of the day instead of after field activity.
- GPS verification is misunderstood as continuous tracking.
- Reps feel the app adds extra admin work.
- Managers expect results too quickly.
- The pilot is judged only by units instead of activity, leads, follow-ups, and productivity.
- Users enter incomplete data.
- The founder tries to add features during the pilot instead of running the pilot.
- The scope expands before the first pilot is completed.
- No one defines what success means before launch.

## 8. How To Recover If Pilot Adoption Drops

If adoption drops, do not blame the users first. Diagnose the workflow.

Recovery process:

1. Identify the drop.
   - Which user stopped logging?
   - Which metric is missing?
   - When did usage drop?

2. Ask the user one simple question.
   - "What made it hard to use Prometheus IQ in the field today?"

3. Separate causes.
   - Confusion.
   - Forgot.
   - Too much data entry.
   - Bad timing.
   - Technical issue.
   - No manager reinforcement.

4. Reduce friction.
   - Re-explain the required fields.
   - Remind users to log immediately after a visit.
   - Keep notes short.
   - Do not ask for unnecessary information.

5. Reset expectations.
   - "The goal is not perfect data. The goal is consistent useful data."

6. Report the recovery.
   - Track the issue and whether it improved after correction.

## 9. What Data Should Be Collected Daily

Daily required data:

- Approved users active.
- Locations visited.
- GPS verified visits.
- LSM events attended.
- Conversations logged.
- Leads generated.
- Membership units sold.
- Follow-ups created.
- Follow-ups completed.
- Time spent in field.
- Productivity per field session.
- Best performing location.
- Best performing time window.
- User feedback.
- Manager feedback.
- Any issue or concern.

Do not collect unnecessary personal information. Keep the pilot focused on approved field-sales activity.

## 10. Final Report Preparation Process

Start preparing the final report during the pilot, not after it ends.

Daily report preparation:

- Save daily metrics.
- Save user feedback.
- Save manager feedback.
- Note any adoption issues.
- Note any GPS/privacy concerns.
- Note strongest field sessions.
- Note missed follow-ups or incomplete logs.

Final report structure:

1. Pilot overview.
   - Dates.
   - Users.
   - Scope.
   - Reviewers.

2. Executive result.
   - One paragraph explaining whether Prometheus IQ improved visibility, accountability, route usefulness, or measurable outcomes.

3. Metrics summary.
   - Locations visited.
   - GPS verified visits.
   - LSM events attended.
   - Leads generated.
   - Units sold.
   - Conversion rate.
   - Follow-ups completed.
   - Time spent in field.
   - Productivity per field session.

4. What worked.
   - Strongest location.
   - Strongest category.
   - Strongest time window.
   - Strongest user feedback.
   - Strongest manager insight.

5. What did not work.
   - Adoption gaps.
   - Missing data.
   - User friction.
   - Manager concerns.

6. Recommendation.
   - Stop pilot.
   - Extend pilot.
   - Expand to a larger controlled pilot.
   - Begin formal business discussion.

## Operating Rule

During the pilot, the founder’s job is not to keep building. The founder’s job is to make sure the pilot runs cleanly, users adopt the workflow, data is captured consistently, and leadership receives a clear final report.
