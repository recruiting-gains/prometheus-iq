## Purpose

This repair preserves every existing founder-attended local artifact while allowing repeated read-only diagnostics to record fresh evidence safely. The failure being repaired was local only: the GET-only command remained fail-closed, but it reused one v2 artifact root and therefore could not save a new diagnostic after earlier completed attempts had already populated that directory.

## Namespace Design

The source now uses immutable per-attempt namespaces rooted under the existing repair directory:

- `$HOME/.prometheus/infrastructure/cloudflare-founder-attended-create-receipt-v2/attempts/<attemptId>/...`

Each fresh GET-only diagnostic creates one exclusive opaque `attemptId` directory generated by the local runtime. The caller does not choose the path. Every attempt directory remains `0700`, every written file remains `0600`, and prior evidence is never deleted, renamed, reused, migrated, or overwritten.

The attempt lineage is reserved after attended confirmation, governed Keychain validation, and clean repository identity validation, but before network. If the remote GET fails closed, that attempt remains an isolated abandoned lineage-only namespace and is ignored by later eligible selection.

Within one attempt, the following artifacts are lineage-bound to the same immutable identifier:

- `attempt-lineage.json`
- `diagnostic-receipt.json`
- `diagnostic-consumption.json`
- `successor-control.json`
- `successor-control-consumption.json`
- `phase-evidence/*`
- `create-receipt-classifications/*` for the later v2 create-receipt path

Cross-attempt substitution fails closed. Old flat-root evidence is preserved byte-for-byte and ignored by the new selector logic.

## Fixed Collision Boundary

If a fresh attempt directory cannot be created exclusively, the workflow emits the fixed nonsecret reason:

- `LOCAL_ARTIFACT_COLLISION`

No secret, account ID, client ID, credential, response body, header, cookie, or path-sensitive value is emitted.

## Preserved Runtime Boundaries

- no Cloudflare API calls during implementation
- no real Keychain reads or writes during implementation
- no token creation or deletion during implementation
- no deployment
- no production mutation

The one-POST ceiling, no-retry behavior, separate Founder confirmations, Keychain rollback rules, and bounded compensation rules are unchanged.
